# 베어메탈 LoadBalancer (kube-vip vs MetalLB)

<br />
<br />

* 베어메탈(On-Premise) 환경에서 외부 접속용 IP(EXTERNAL-IP)를 부여하는 기능

---

```
AWS 같은 클라우드 환경에서는 Service의 타입을 LoadBalancer로 설정하면,
클라우드 사업자가 알아서 외부 접속용 IP(ELB)를 할당해 준다.

하지만 직접 구축한 베어메탈 서버나 Hyper-V 가상머신 환경에서는 
외부 IP를 할당해 주는 주체가 없기 때문에 EXTERNAL-IP가 무한히 <pending> 상태에 빠진다.

이를 해결하기 위해 클러스터 내부에 직접 설치하는 도구가 kube-vip와 MetalLB이다.
```

<br />
<br />
<br />
<br />

1. 가장 중요한 핵심 개념 (로드밸런싱에 대한 오해)

<br />

`1) kube-vip와 MetalLB는 트래픽을 분산하는 로드밸런서가 아니다.`

```
이름 때문에 이 도구들이 트래픽을 여러 노드로 쪼개주는 로드밸런서라고 오해하기 쉽다.

하지만(ARP 모드 기준) 이 도구들의 진짜 역할은 단 하나이다.

"외부에서 들어올 수 있는 가상 IP(VIP)를 특정 노드 1대(리더)에 연결해 주고,
그 노드가 죽으면 즉시 다른 노드로 IP를 옮겨주는 고가용성(Failover) 문지기" 역할만 수행한다.
```

<br />

`2) 진짜 트래픽 분산(Load Balancing)은 kube-proxy가 한다.`

```
리더 노드가 가상 IP(예: 192.168.0.240)를 통해 외부 패킷을 일단 받아들이면,
그 순간부터 해당 노드 안의 리눅스 커널(kube-proxy / iptables)이 패킷을 낚아챈다.

그리고 클러스터 내 모든 워커 노드에 퍼져 있는 파드(Ingress Controller 등)들에게
50:50 비율로 공평하게 트래픽을 분산시켜 준다.
```

<br />
<br />
<br />

2. kube-vip의 특징과 구조

```
kube-vip는 단일 파드 종류(DaemonSet)만으로 가볍게 동작하며,
리더로 선출된 노드의 실제 리눅스 랜카드(eth0)에 보조 IP를 직접 등록하는 방식을 사용한다.

* 데몬셋(DaemonSet) - 클러스터의 각 노드마다 파드를 딱 1개씩만 배치하는 컨트롤러
```

<br />

`1) 동작 방식`

```
1. 각 노드에 떠 있는 kube-vip 파드들이 쿠버네티스 API 서버의 Lease(임대 계약서)를 통해 리더를 1명 뽑는다.

2. 리더가 된 노드의 kube-vip 파드는 자기 노드의 랜카드(eth0)에 가상 IP(240)를 보조 IP로 직접 추가한다.
   (노드에서 ip addr 명령어를 치면 실제로 192.168.0.240이 보인다.)

3. 공유기에게 "240번 IP는 내 랜카드(MAC 주소)로 보내라"고 ARP 신호를 보낸다.

4. 리더 노드가 다운되면, 다른 노드의 kube-vip가 즉시 자기 랜카드에 240번 IP를 등록하고 권한을 이어받는다.
```

<br />

`2) 구조도`

```
+-----------------------------------------------------------------+
|   쿠버네티스 클러스터                                                |
|                                                                 |
|   +-------------------------+       +-------------------------+ |
|   | 워커 노드 1 (리더 당첨)     |       | 워커 노드 2 (대기 중)       | |
|   |                         |       |                         | |
|   |  +-------------------+  |       |  +-------------------+  | |
|   |  | kube-vip 파드      |  |       |  | kube-vip 파드      |  | |
|   |  | (데몬셋)           |  |       |  | (데몬셋)            |  | |
|   |  +-------------------+  |       |  +-------------------+  | |
|   |            |            |       |                         | |
|   |     (랜카드에 직접 등록)    |       |     (리더 감시 대기)        | |
|   |            v            |       |                         | |
|   |  +-------------------+  |       |  +-------------------+  | |
|   |  | 랜카드 (eth0)      |  |       |  | 랜카드 (eth0)       |  | |
|   |  | 본래 IP: .102      |  |       |  | 본래 IP: .103      |  | |
|   |  | 보조 IP: .240 (VIP)|  |       |  | 보조 IP: 없음       |  | |
|   |  +-------------------+  |       |  +-------------------+  | |
|   +-------------------------+       +-------------------------+ |
|                ^                                                |
+----------------|------------------------------------------------+
                 |
        (240으로 외부 요청 유입 -> 진입 후 kube-proxy가 양쪽 노드로 분산)
```

3. MetalLB의 특징과 구조

```
MetalLB는 여러 개의 IP 대역(IP Pool)을 관리하는 데 특화되어 있으며,
역할을 두 가지 파드(Controller, Speaker)로 철저히 나누어 동작한다.

특이한 점은 랜카드에 IP를 직접 등록하지 않고, ARP 네트워크 응답만 가로채서 패킷을 받아낸다.
```

<br />

`1) 두 파드의 역할 분담`

```
* Controller 파드 (Deployment - 클러스터 전체에 딱 1개만 존재)
  - 새로운 LoadBalancer 타입의 서비스가 생기면, 설정된 IP Pool(예: 240~245)에서
    남는 IP 번호표를 하나 꺼내 그 서비스에 할당(도장 쾅)해 주는 행정 직원이다.
  - 누가 리더가 될지 관여하지 않고 오직 IP 장부 관리만 한다.

* Speaker 파드 (DaemonSet - 각 노드마다 1개씩 존재)
  - 자기들끼리 자체 통신(Memberlist 프로토콜)을 하며 생존 신고를 주고받는다.
  - 살아있는 노드들의 이름과 할당된 IP를 조합해 자체 계산(해시 알고리즘)을 돌려 1순위(리더)를 정한다.
  - 1순위가 된 Speaker는 랜카드에 IP를 등록하지 않고, 공유기가 "240번 누구야?"라고 물을 때
    "나야!"라고 대신 대답만 해서 패킷을 자기 노드로 유인한다.
```

<br />

`2) 구조도`

```
+-----------------------------------------------------------------+
|   쿠버네티스 클러스터                                                |
|                                                                 |
|   +---------------------------------------------------------+   |
|   | Controller 파드 (디플로이먼트 - 전체 1개)                     |   |
|   | "IP Pool(240~245)에서 빈 번호표를 꺼내 서비스에 부여함"          |   |
|   +---------------------------------------------------------+   |
|                                |                                |
|                         (IP 번호표 배정)                           |
|                                v                                |
|   +-------------------------+     +-------------------------+   |
|   | 워커 노드 1 (1순위 당첨)    |     | 워커 노드 2 (2순위 대기)     |   |
|   |                         |     |                         |   |
|   |  +-------------------+  |     |  +-------------------+  |   |
|   |  | Speaker 파드       | <-----> | Speaker 파드         |  |   |
|   |  | (데몬셋)           | (생존확인) | (데몬셋)             |   |   |
|   |  +-------------------+  |     |  +-------------------+  |   |
|   |            |            |     |                         |   |
|   |   (랜카드 등록 없이         |     |                         |   |
|   |    공유기에 응답만 함)      |     |                          |   |
|   +------------|------------+     +-------------------------+   |
|                ^                                                |
+----------------|------------------------------------------------+
                 |
        (240으로 외부 요청 유입 -> 진입 후 kube-proxy가 양쪽 노드로 분산)
```

4. kube-vip vs MetalLB 핵심 비교 및 선택 기준

<br />

| 비교 항목 | kube-vip | MetalLB |
|:---:|---|---|
| **설치 형태** | DaemonSet 단독 (가벼움) | Controller(Deployment) + Speaker(DaemonSet) |
| **IP 등록 방식** | 리눅스 랜카드(`eth0`)에 보조 IP를 실제로 등록함 (`ip a`로 보임) | 랜카드에 등록하지 않고 네트워크(ARP) 응답만 대신 보냄 (`ip a`로 안 보임) |
| **노드 간 생존 확인** | 쿠버네티스 기본 Lease API 활용 | Speaker끼리 자체 통신(포트 7946) 사용 |
| **주요 목적** | 단일 진입점(VIP 1개) 구성 및 마스터 노드(6443) 이중화 | 다수의 LoadBalancer 서비스에 여러 IP(IP Pool) 자동 배급 |

<br />

`결론: 언제 무엇을 써야 하는가?`

```
1) kube-vip가 유리한 경우 (홈랩 / 단일 공유기 포트포워딩 환경)
   - 외부에서 들어오는 공인 IP가 1개뿐이고, 공유기에서 80/443 포트를 내부 IP 1개(예: 240)로만 포워딩할 때.
   - 내부 라우팅은 어차피 Ingress Controller(Traefik, Nginx)가 도메인과 경로를 보고 다 처리하므로,
     여러 개의 IP Pool이 필요 없고 가볍고 직관적인 구성을 원할 때 가장 적합하다.

2) MetalLB가 유리한 경우 (사내망 다중 서비스 / 비 HTTP 포트 다수 사용)
   - 클러스터 내부에 DB, GitLab(SSH 22번 포트), 게임 서버 등 Ingress(80/443)로 묶기 힘든
     별도의 LoadBalancer 서비스가 여러 개 필요할 때.
   - IP Pool(240~250)을 지정해 두고 각 서비스마다 전용 사설 IP를 하나씩 나눠주어
     사내망에서 각자 다른 IP로 접속하게 만들고 싶을 때 적합하다.
```
