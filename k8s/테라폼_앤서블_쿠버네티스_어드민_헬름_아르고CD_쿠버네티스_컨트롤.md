# K8s 배포까지 전체 자동화 파이프라인을 위한 기술들을 알아보자.

<br />
<br />

* 인프라 구축부터 앱 무중단 배포까지 자동화하는 도구들의 역할과 흐름

---

```
쿠버네티스(K8s)는 컨테이너화된 앱을 운영하기에 훌륭한 도구이다.

하지만 빈 땅에 서버(VM)를 만들고, 리눅스 설정을 맞추고, 쿠버네티스를 설치한 뒤,
수십 개의 YAML 파일을 관리하고 배포하는 과정을 사람이 일일이 손으로 치는 것은 매우 고통스럽다.

그래서 현업에서는 각 단계마다 전문 자동화 도구들을 연결하여 파이프라인을 구축한다.

쉽게 이해할 수 있도록 '아파트를 짓고 입주하는 과정'에 비유하여 전체 흐름과 각 도구의 역할을 살펴보자.
```

<br />

1. 한눈에 보는 전체 자동화 흐름도 (집 짓기 비유)

```
+-----------------------------------------------------------------------------------+
|                        [1단계: 인프라 구축 (땅 파고 건물 올리기)]                         |
|                                                                                   |
|  [1. Terraform]  ---> 빈 땅(AWS, Hyper-V 등)에 가상머신(VM)과 네트워크를 자동으로 생성       |
|        |                                                                          |
|        v                                                                          |
|  [2. Ansible]    ---> 생성된 깡통 VM들에 접속해 리눅스 초기 설정(Swap 끄기 등) 일괄 수행       |
|        |                                                                          |
|        v                                                                          |
|  [3. Kubeadm/K3s] --> 세팅된 VM들을 묶어 마스터/워커 노드로 이루어진 K8s 클러스터 완성          |
+-----------------------------------------------------------------------------------+
                                         |
                                         v
+-----------------------------------------------------------------------------------+
|                        [2단계: 앱 패키징 및 배포 (가구 배치 및 관리)]                      |
|                                                                                   |
|  [4. Helm]       ---> 복잡한 YAML 파일들을 '변수 처리된 템플릿(패키지)'으로 깔끔하게 묶음        |
|        |                                                                          |
|        v                                                                          |
|  [5. ArgoCD]     ---> Git 저장소를 감시하다가 코드가 바뀌면 클러스터에 자동으로 배포 동기화       |
|        |                                                                          |
|        v                                                                          |
|  [6. Kubectl]    ---> 관리자가 클러스터 상태를 직접 조회하거나 수동 명령을 내리는 리모컨          |
+-----------------------------------------------------------------------------------+
```

2. 단계별 핵심 도구 상세 설명

<br />

`1) Terraform (테라폼) -> "마우스로 VM 만들지 말고 코드로 한 방에 찍어내자"`

```
* 비유 -> 빈 땅에 건물 골조(서버, 공유기, 방화벽)를 설계도대로 한 번에 세우는 중장비

* 왜 필요한가?
  AWS 콘솔이나 Hyper-V 관리자 창에서 마우스로 일일이 클릭하며 VM 10대를 만들고 IP를 부여하면
  시간도 오래 걸리고 실수가 발생한다.

  테라폼은 코드 파일에 "CPU 4코어, RAM 16GB짜리 VM 3대 만들어줘"라고 적어두고 명령어 한 줄만 치면
  클라우드나 하이퍼바이저에 똑같은 스펙의 VM과 네트워크를 몇 분 만에 자동으로 생성해 준다.
```

<br />

`2) Ansible (앤서블) -> "VM 10대에 일일이 SSH 접속해서 명령어 치지 말자"`

```
* 비유 -> 지어진 건물 각 방을 돌아다니며 벽지를 바르고 전기 배선을 깔아주는 인테리어 업자

* 왜 필요한가?
  테라폼이 깡통 리눅스 VM 10대를 만들어 주었다고 치자.

  여기에 쿠버네티스를 깔려면 10대 모두에 SSH로 접속해서 스왑 메모리를 끄고(swapoff),
  방화벽을 열고, 커널 설정을 바꾸는 똑같은 작업을 10번 반복해야 한다.

  앤서블은 내 PC에서 작업 지시서(Playbook) 하나만 실행하면, 10대의 VM에 동시에 접속해
  이 모든 리눅스 사전 설정과 패키지 설치를 자동으로 끝내준다.
```

<br />

`3) Kubeadm 또는 K3s -> "세팅된 리눅스 서버들을 쿠버네티스 클러스터로 합체시키자"`

```
* 비유 -> 각 방을 연결하여 실제로 사람이 살 수 있는 아파트 시스템으로 가동시키는 작업

* 왜 필요한가?
  리눅스 사전 설정이 끝난 VM들에 실제 쿠버네티스 엔진을 올리고,
  "1번 VM은 마스터 노드가 되고, 2번과 3번 VM은 워커 노드로 마스터에 합류(Join)해라"라고
  클러스터를 초기화해 주는 도구이다.
  (정통 쿠버네티스는 Kubeadm을 주로 쓰고, 경량화 환경에서는 설치가 훨씬 간편한 K3s를 사용한다.)
```

<br />

`4) Helm (헬름) -> "비슷한 YAML 파일 수십 개를 복붙하지 말고 템플릿과 패키지 매니저로 쓰자"`

```
* 비유 -> 이케아(IKEA) 가구 조립 세트 또는 리눅스의 apt / 노드의 npm

* 왜 필요한가?
  1. 템플릿 기능 -> 개발 서버와 운영 서버에 배포할 때 YAML 내용은 99% 똑같고 도메인이나 파드 개수만 다르다.
     헬름을 쓰면 YAML에 빈칸({{ .Values.replicas }})을 뚫어놓고, 환경별 변수 파일(values.yaml)만 바꿔 끼워 재사용할 수 있다.

  2. 앱스토어 기능 -> 남들이 이미 완벽하게 만들어 둔 프로그램(cert-manager, Traefik, Prometheus 등)을
     복잡한 YAML 작성 없이 helm install 한 줄로 내 클러스터에 쉽게 설치할 수 있다.
```

<br />

`5) ArgoCD (아르고CD) -> "내 손으로 kubectl apply 치지 말고 Git에 올리면 알아서 배포되게 하자"`

```
* 비유 -> 설계도(Git)와 실제 방 상태(클러스터)를 24시간 비교하며 똑같이 맞춰놓는 자동 관리 로봇

* 왜 필요한가? (GitOps의 핵심)
  과거에는 개발자가 터미널을 열고 직접 kubectl apply -f deployment.yaml을 쳤다.

  이러면 누가 언제 어떤 버전을 배포했는지 알기 어렵고, 장애가 났을 때 이전 버전으로 되돌리기도 힘들다.

  ArgoCD는 클러스터 내부에 파드로 떠서 우리의 Git 저장소를 24시간 감시한다.

  우리가 Git에서 YAML 파일의 이미지 버전 숫자만 바꾸고 Push(커밋)하면,
  ArgoCD가 이를 감지하고 클러스터에 자동으로 배포(Sync)해 주며, 배포 상태를 예쁜 웹 화면으로 보여준다.
```

<br />

`6) Kubectl (큐브 컨트롤) -> "클러스터에 직접 명령을 내리는 관리자 리모컨"`

```
* 비유 -> 건물 관리소장이 상태를 점검하고 수동 조작할 때 쓰는 마스터키와 무전기

* 왜 필요한가?
  마스터 노드의 API Server와 직접 통신하는 명령어 도구이다.

  ArgoCD 같은 자동화 도구를 쓰더라도, 현재 파드가 잘 떠 있는지 확인(get pods)하거나,
  에러 로그를 보고(logs), 문제를 디버깅(describe)할 때 관리자가 가장 많이 사용하는 기본 도구이다.
```

3. 전체 자동화 파이프라인 요약 표

| 순서 | 단계 | 주요 도구 | 관리 대상 | 핵심 역할 (한 줄 요약) | 실제 수행 작업 예시 |
|:---:|------|----------|----------|-----------------------|-------------------|
| **1** | **인프라 생성 (IaC)** | **Terraform** | 클라우드 / 하이퍼바이저 | 빈 땅에 **깡통 VM과 네트워크**를 코드로 자동 생성 | VPC, 서브넷 생성 및 Master/Worker용 빈 VM 인스턴스 생성 |
| **2** | **OS 사전 설정** | **Ansible** | VM 내부 (Linux OS) | 여러 VM에 동시 접속해 **리눅스 기초 세팅** 일괄 자동화 | Swap 메모리 비활성화, 커널 모듈 로드, 방화벽 오픈, 필수 패키지 설치 |
| **3** | **클러스터 구축** | **Kubeadm / K3s** | 쿠버네티스 클러스터 | 세팅된 VM들을 묶어 **마스터/워커 클러스터**로 초기화 | 마스터 노드 초기화(`init`) 및 토큰을 이용해 워커 노드 조인(`join`) |
| **4** | **앱 패키징** | **Helm** | K8s YAML 파일들 | 여러 YAML을 **변수화(템플릿)**하고 한 세트로 묶어 관리 | `values.yaml`에 이미지 태그와 파드 수를 정의해 환경별로 재사용 |
| **5** | **자동 배포 (GitOps)** | **ArgoCD** | Git 저장소 <-> 클러스터 | **Git에 올라온 YAML 변경사항**을 클러스터에 자동 반영 | Git에 새 버전 커밋 시 이를 감지해 자동으로 `apply` 및 상태 동기화 |
| **6** | **조회 및 제어** | **Kubectl** | 쿠버네티스 API 서버 | 관리자가 클러스터 상태를 **직접 확인하고 제어**하는 도구 | `kubectl get pods`, `kubectl logs`로 상태 확인 및 트러블슈팅 |

* TIP -> 우리 환경(베어메탈 + K3s)에서는 어디까지 쓰는 게 좋을까?

```
1. Terraform + Ansible (1~2단계)
   클라우드에서 서버 수십 대를 수시로 만들었다 지웠다 할 때 필수이다.

   우리처럼 베어메탈 서버 1대에 VM 3~4개를 고정으로 한 번만 만들어서 계속 쓸 때는,
   오히려 테라폼과 앤서블을 배우고 세팅하는 시간이 더 걸리므로 직접 생성하는 것이 훨씬 효율적이다.


2. Helm + ArgoCD (4~5단계)
   클러스터 구축이 끝난 뒤, 앞으로 프론트(Next)와 백엔드(Nest) 앱을 수십, 수백 번 업데이트할 때
   매번 서버에 접속해서 kubectl apply를 치는 수고를 덜어준다.

   추후 배포 자동화(CI/CD)를 고도화할 때 가장 먼저 도입해 볼 만한 가치가 있는 도구들이다.
```
